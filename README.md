# Vehicle Damage Type Detection

**AI Assignment — Topic 6: Image Processing & Computer Vision**

Classify the **type** of damage on a vehicle from a photo, using the **CarDD**
dataset. Six damage types: `dent`, `scratch`, `crack`, `glass_shatter`,
`lamp_broken`, `tire_flat`.

## ▶ Try it: <https://car-damage-demo.vercel.app>

Deployed and live — upload any photo of vehicle damage and it classifies it. No
install, no sign-in, works on a phone.

**Project status:** all three algorithms are trained and evaluated, and the CNN is
deployed as a live web app.

---

## Algorithm allocation

The assignment requires each member to solve the task with a **different algorithm**,
then compare accuracy / precision / recall / F1. All three read the **same crops and
the same splits**, so the comparison is fair.

| Member | Algorithm | Family | Entry point | Status |
|--------|-----------|--------|-------------|--------|
| **A** | **MobileNetV2 CNN**, transfer learning from ImageNet | Deep learning | `src/train_cnn.py` | **Trained & evaluated** |
| **B** | **SVM (RBF kernel)** on HOG features | Classical ML | `src/train_svm.py` | **Trained & evaluated** |
| **C** | **YOLOv8** object detection | Deep learning, detection | `src/train_yolo.py` | **Trained & evaluated** |

Files are named after the algorithm, not the member, so the codebase stays readable
if the allocation ever changes. This table is the only place the mapping lives.

**Why these three.** They differ on the axis that matters: A learns its own features
from pixels; B uses features a human designed (HOG describes edge-orientation
histograms) and a classifier that never sees a pixel directly; C solves a strictly
harder problem — it must *locate* the damage as well as name it.

**The SVM's secondary runs.** `train_svm.py` also supports `--model knn` and
`--feature flatten`. Those stay available as ablations in the write-up — SVM + HOG
is the headline result, KNN and raw pixels are the comparison that shows why.

**YOLO is not directly comparable, and the report must say so.** Detection is
scored with mAP and IoU because a prediction is only correct if the box overlaps the
true region. Putting YOLO's mAP in the same column as A's accuracy would be an
apples-to-oranges error a marker will notice. Report C separately and compare it on
per-class detection quality instead.

Two findings worth writing up:

- **Macro-F1 (0.944) exceeds accuracy (0.924)** because the classes handled perfectly

  classes lift the macro average.
- **41 of 59 total errors are dent ↔ scratch**, plus 7 more crack → scratch. Almost
  all error is surface damage bleeding together — expected, since on a cropped patch
  a dent and a scratch differ mainly in shading, not shape.

| Algorithm | Accuracy | Precision (macro) | Recall (macro) | F1 (macro) |
|-----------|---------:|------------------:|---------------:|-----------:|
| **cnn** | 0.9239 | 0.9517 | 0.9379 | **0.9439** |
| svm_hog | 0.7045 | 0.7522 | 0.6434 | 0.6858 |
| svm_flatten | 0.5961 | 0.5964 | 0.5129 | 0.5422 |
| knn_hog | 0.5458 | 0.6067 | 0.5340 | 0.5258 |
| knn_flatten | 0.4645 | 0.7326 | 0.3004 | 0.3227 |

Per-class F1:

| Class | cnn | svm_hog | svm_flatten | knn_hog | knn_flatten |
|-------|----:|--------:|------------:|--------:|------------:|
| crack | 0.8926 | 0.5000 | 0.3800 | 0.3297 | 0.2025 |
| dent | 0.8953 | 0.7000 | 0.5745 | 0.4444 | 0.4180 |
| glass_shatter | 0.9857 | 0.6299 | 0.3063 | 0.4252 | 0.0278 |
| lamp_broken | 0.9714 | 0.6613 | 0.5645 | 0.4200 | 0.1351 |
| scratch | 0.9182 | 0.7462 | 0.6822 | 0.6687 | 0.5749 |
| tire_flat | 1.0000 | 0.8772 | 0.7458 | 0.8667 | 0.5778 |

**What this shows**, with each effect isolated by one variable:

1. **Learned features beat hand-designed ones, by a lot.** 0.944 against the best
   classical result of 0.686 is a 0.26 gap in macro-F1. It comes from the CNN
   discovering what to look at rather than being told to look at edge orientations.
2. **Features matter as much as the classifier.** Pixels → HOG lifts SVM by 0.14 F1
   and KNN by 0.20. KNN → SVM on the same features lifts by 0.16 and 0.22. Both
   changes are real, and they are roughly the same size.
3. **The per-class table shows *where* the classical methods fail.** `tire_flat` is
   easy for everything — 0.877 even for KNN — because a flat tyre has a distinctive
   global shape. `glass_shatter` collapses from 0.986 to 0.028 for KNN on raw pixels,
   because its signal is fine-grained texture: HOG preserves it, 64×64 greyscale
   downsampling destroys it.

**A trap worth pointing out in the write-up:** `knn_flatten` has the second-highest
macro *precision* (0.733) and by far the worst F1 (0.323). It buys that precision by
almost never predicting the hard classes — 1.000 precision on `glass_shatter` from
exactly 1 correct prediction out of 71. Quoting precision alone would badly
misrepresent it, which is precisely why the rubric asks for F1.

### Detection (separate table on purpose)

| Algorithm | Precision | Recall | mAP@50 | mAP@50-95 |
|-----------|----------:|-------:|-------:|----------:|
| yolo | 0.6338 | 0.5663 | **0.6021** | 0.4869 |

YOLOv8n, 10 epochs at 416 px on CPU, 2,816 training images.

These numbers are **not** a row in the table above, and the report should keep them
apart. Detection is scored with mAP and IoU because a prediction only counts if the box
overlaps the true region — YOLO is answering "where is the damage, and what is each
one?" while the classifiers answer "what is this crop?". A model can score 0.60 mAP on
the harder question while a classifier scores 0.92 accuracy on the easier one, and
neither number makes the other look good or bad.

**The run was compute-limited and had not converged**: mAP@50 rose 0.583 → 0.602 on
the final epoch, and mAP@50-95 rose 0.459 → 0.487. That is worth stating in the
write-up, with `results/yolo/cardd/results.png` as evidence. A 50-epoch run at 640 px
on a GPU would land meaningfully higher.

.venv\Scripts\python src\train_yolo.py --data "data\raw\cardd\data.yaml" --epochs 10 --img-size 416
.venv\Scripts\python src\compare.py

## How the codebase works

### The core idea

CarDD ships as an **object-detection** dataset: each image has a `.txt` file listing
bounding boxes in YOLO format (`class_id cx cy w h`, normalised). The CNN and the SVM
need a **classification** dataset — one label per image.

The pipeline bridges that gap by **cropping every labelled box into its own image**,
filed under its class name. One photo with three damaged regions becomes three
training images. YOLO skips this entirely and trains on the original boxes.

### Data flow

```
Kaggle CarDD (~3 GB)
        │  src/download_data.py
        ▼
data/raw/cardd/            images + YOLO .txt labels + data.yaml
        │                                    │
        │  src/prepare_classification.py     └────────────┐
        ▼                                                 │
data/classification/<split>/<class>/*.jpg                 │
   6,084 train · 1,719 val · 775 test                     │
        │                                                 │
   ┌────┴──────────────┐                                  │
   ▼                   ▼                                  ▼
   CNN                 SVM                              YOLO
train_cnn.py        train_svm.py                     train_yolo.py
   │                                                  (trains on raw boxes)
   ▼
models/cnn_damage_classifier.pth
   │
   ├── src/evaluate.py ──► results/ (metrics, confusion matrix)
   └── notebooks/export_onnx.ipynb ──► .onnx ──► the web demo
```

### Stage 1 — Acquisition · `src/download_data.py`

Downloads the CarDD archive straight from Kaggle's REST API using a bearer token read
from `~/.kaggle/kaggle.json`. Written to survive a bad connection: it resumes via HTTP
`Range` headers and retries up to 12 times, which matters for a ~3 GB download.

Extracts to `data/raw/cardd/`, records where it landed in `data/raw_path.txt` so the
next stage can find it, deletes the zip, and prints the folder tree.

### Stage 2 — Preparation · `src/prepare_classification.py`

The most involved script in the repo. In order:

1. **Locates the raw data** via `data/raw_path.txt`.
2. **Reads the class names** from the dataset's own `data.yaml`, so the label ids in
   the `.txt` files map to the right names. Falls back to `config.CLASS_NAMES`.
3. **Pairs each label file with its image** by filename stem.
4. **Parses each box** and converts normalised YOLO coordinates to pixels.
5. **Crops with 10% padding** (`config.BOX_PADDING`) so the model sees a little
   context, and **skips boxes under 24 px** (`config.MIN_BOX_SIZE`) as too small to
   learn from.
6. **Splits the data.** If at least half the records carry a train/val/test hint from
   the dataset's own folder layout, it honours those. Otherwise it makes a seeded
   random split at the *image* level — never the box level, so crops from one photo
   cannot leak across splits.
7. **Wipes `data/classification/` first**, then writes crops to
   `<split>/<class_name>/`.

### Stage 3 — Shared foundation

Four modules the algorithms sit on:

| File | Role |
|------|------|
| `src/config.py` | Single source of paths and hyper-parameters. Edit here, not in the scripts. |
| `src/utils.py` | `set_seed` (random + numpy + torch), `get_device` (CUDA if present), `save_json`, and the two plotters. |
| `src/dataset.py` | Transforms and dataloaders. |
| `src/model.py` | Builds the network. |

**`dataset.py`** defines two transform pipelines. Training applies light augmentation —
horizontal flip, ±15° rotation, colour jitter — to fight overfitting on a small
dataset. Evaluation only resizes and normalises. Both normalise with **ImageNet
mean/std**, which is required: the pretrained backbone was trained on inputs scaled
that way. Dataloaders are plain `torchvision.ImageFolder`, which reads
`<split>/<class>/` directly.

**`model.py`** implements transfer learning. It loads a torchvision backbone with
ImageNet weights, then **replaces only the final classification layer** with a fresh
one sized to 6 classes. `--freeze-backbone` optionally trains just that new head.
Supports `resnet18`, `resnet50`, `mobilenet_v2` and `efficientnet_b0`.

### Stage 4 — CNN

**`src/train_cnn.py`** runs the training loop. Adam with weight decay, cross-entropy
loss, and after every epoch it evaluates on the validation split.

The important detail: it **keeps the checkpoint with the best validation macro-F1**,
not the last epoch. Validation loss bottoms out around epoch 5 and rises after, while
macro-F1 keeps drifting up to epoch 14 — so this choice is what rescued the run from
mild overfitting. The saved checkpoint is a dict of `state_dict`, `class_names`,
`backbone` and `img_size`, which makes it self-describing: evaluation and inference
rebuild the exact architecture from the file without being told.

Writes `results/cnn_training_history.json` and `.png`.

**`src/evaluate.py`** loads that checkpoint, runs the held-out test split, and
produces the rubric numbers — accuracy, macro precision/recall/F1, a per-class report,
and a confusion matrix — into `results/`.

**`src/predict.py`** classifies a single image and prints the top-k probabilities.

### Stage 5 — SVM

**`src/train_svm.py`** deliberately shares no code with the CNN beyond `config`
and `utils`, because the whole point is a different pipeline:

```
image ─► 64×64 greyscale ─► HOG or flattened pixels ─► StandardScaler ─► SVM / KNN
```

No convolution, no learned features, no GPU. Scaling matters here in a way it does not
for the CNN: SVM's RBF kernel is distance-based, so unscaled features would let one
dimension dominate.

### Stage 6 — YOLO

**`src/train_yolo.py`** wraps Ultralytics YOLO. It ignores
`data/classification/` and trains on the **original** CarDD labels via the dataset's
`data.yaml`, because detection needs the boxes the cropping stage threw away. This is
why `data/raw/` must not be deleted. Ultralytics writes its own metrics and plots into
`results/yolo/`.

### Stage 7 — Export and the web demo

**`notebooks/export_onnx.ipynb`** converts the trained `.pth` into ONNX, verifies the
export matches PyTorch numerically, and also exports a stock ImageNet MobileNetV2 used
by the demo's vehicle check. It asserts the result is a **single self-contained file** —
an ONNX that leaves its `.onnx.data` sidecar behind loads fine locally and fails on a
server.

The demo is **live at <https://car-damage-demo.vercel.app>**. Its code lives in a
separate repo, [`car-damage-demo`](https://github.com/Avocado39/car-damage-demo), so
this one stays focused on training. Pushing to that repo redeploys it automatically.

It runs **ONNX Runtime** rather than PyTorch, which is what lets it run on a Smart App
Control machine at all, and keeps the serverless bundle under Vercel's 500 MB limit.
The browser downscales uploads to 1024 px before sending — the model resizes to
224×224 anyway, so this costs no accuracy and keeps requests under the 4.5 MB body
limit that phone photos would otherwise breach.

It also runs a second model to warn when the upload does not look like a vehicle. The
damage classifier ends in a softmax over six classes and has no "none of the above"
option, so without that warning a photo of a bicycle still returns six confident
damage probabilities.

## Environment: two constraints

**1. Python 3.12, not 3.14.** ML wheels are not published for 3.14. Use the `.venv/`:

```powershell
.venv\Scripts\python <script>
```

Recreate it elsewhere with:

```powershell
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
```

**2. No GPU, and PyTorch may be blocked.** Windows **Smart App Control** is enabled on
the dev machine. Earlier torch builds failed to load with:

```
OSError: [WinError 4551] An Application Control policy has blocked this file.
```

Smart App Control judges binaries by signature and cloud reputation, and torch's
Windows DLLs are unsigned. `torch 2.13.0+cpu` now loads fine — presumably having
earned enough reputation — but a different build could be blocked again. If that
happens, it is not fixable in Python: Smart App Control can only be disabled, which is
irreversible without a Windows reinstall. Use the Colab notebooks instead.

Either way the machine is **CPU-only** (`torch.cuda.is_available()` is `False`), so
GPU-bound work belongs on Colab for speed, not correctness.

### What runs where

Everything runs locally today. "Colab" below means *much faster there*, not *broken
here*.

| Stage | Script | Local? | Notes |
|-------|--------|--------|-------|
| 1. Download | `src/download_data.py` | Yes | ~3 GB from Kaggle |
| 2. Prepare | `src/prepare_classification.py` | Yes | 1–2 min |

## Running it

### Steps 1–2, locally

```powershell
.venv\Scripts\python src\download_data.py            # needs a Kaggle API token
.venv\Scripts\python src\prepare_classification.py
```

Kaggle token: [kaggle.com/settings](https://www.kaggle.com/settings) → **Create New
API Token** → save `kaggle.json` to `C:\Users\<you>\.kaggle\kaggle.json`.

### Steps 3–4, on Colab

**Already done — the model is trained and the results above are final.** This section
documents how, for the report and for anyone who needs to reproduce it.

The Colab notebooks read the source and dataset from Google Drive. Build the zips:

```powershell
.venv\Scripts\python scripts\make_colab_bundle.py           # source only, ~45 KB
.venv\Scripts\python scripts\make_colab_bundle.py --data    # also the ~360 MB dataset
```

Upload them to `MyDrive/cardd/`, then run
[`notebooks/train_colab.ipynb`](notebooks/train_colab.ipynb) on a T4 GPU. It runs this
repo's own `src/` code rather than a copy, so results stay reproducible, and copies
everything back to Drive so it survives the session ending.

> **Rebuild and re-upload `cardd_src.zip` whenever anything under `src/` changes**,
> and **restart the Colab session** afterwards — the notebooks skip unpacking if
> `/content/AI-Image-Processing` already exists, so a stale copy silently persists.
> A stale bundle fails in a confusing way: the notebook unpacks it, reports success,
> then dies on a missing file. `make_colab_bundle.py` guards against the worst case by
> refusing to write a zip that lacks any script the notebooks invoke.

### SVM, locally

```powershell
.venv\Scripts\python src\train_svm.py                    # svm + hog (the headline)
.venv\Scripts\python src\train_svm.py --model knn --feature flatten
.venv\Scripts\python src\train_svm.py --sweep            # all four combinations
```

Each run writes `results/<model>_<feature>/`. `--sweep` extracts each feature set once
and reuses it across both classifiers, then prints a ranked summary.

### YOLO

```powershell
.venv\Scripts\python -m pip install -r requirements-yolo.txt
.venv\Scripts\python src\train_yolo.py --data "data\raw\cardd\data.yaml" --epochs 10 --img-size 416

# quick smoke run - a fraction of the data, to check the pipeline before committing hours
.venv\Scripts\python src\train_yolo.py --data "data\raw\cardd\data.yaml" --epochs 1 --fraction 0.02
```

CarDD's shipped `data.yaml` hardcodes Kaggle paths (`/kaggle/input/...`), so
`train_yolo.py` detects that and writes a corrected `data_local.yaml` beside it
automatically.

On CPU each epoch is 5–7 minutes at 416 px. On a GPU, use `--epochs 50 --img-size 640`.

## Known gaps

- **No tests.** Nothing here is covered by automated tests.
- **`config.CLASS_NAMES` is YOLO-label order, not model-output order.** The trained
  model uses `ImageFolder`'s alphabetical order (`crack` first); `config.CLASS_NAMES`
  starts with `dent`. Always read class names from the checkpoint, as `evaluate.py`
  and `predict.py` do. Assuming `config.CLASS_NAMES` matches model output will
  silently mislabel every prediction.
- **The YOLO run was compute-limited.** 10 epochs at 416 px on CPU, and mAP was still
  climbing on the final epoch — so 0.602 mAP@50 is a floor, not the model's ceiling.
  [`notebooks/train_yolo_colab.ipynb`](notebooks/train_yolo_colab.ipynb) does the full
  50-epoch 640 px run on a T4 in about an hour and exports the ONNX to upgrade the
  deployed demo. **Not yet run** — the figures above are still the CPU ones.
- **`config.BACKBONE` still defaults to `resnet18`** while the project uses
  MobileNetV2. Pass `--backbone mobilenet_v2` explicitly, as the Colab notebook does.
